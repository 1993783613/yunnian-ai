# 数字人实时化架构评估报告

> 项目：云念 AI（AI 数字亲人视频通话） · 评估人：Bob（架构） · 日期：2026-09-11
> 现状：静态前端 + 腾讯云 SCF（action 路由）+ 腾讯 TRTC v5 拉流 + 腾讯 IVH 照片数字人（仅嘴动、无背景）
> 目标：开口说话 + **背景也在动** + 微信视频通话式实时对话

---

## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
|---|---|
| "背景也在动"能落地吗 | 能，**只有生成式流式模型（A/B 路线）**能真正生成会动的背景；其余三条路都是"假的背景动" |
| 一张逝者照片能驱动吗 | 能。FlowAct-R1 / Vivix-A1 都是单图驱动，无需训练、无需录像 |

| 代码改造最省的是谁 | **Vivix-A1**（官方走 TRTC 传输，`aiIvhTrtc` 进房拉流代码几乎可原样复用） |

## 1. "背景也在动"的技术真相

### 1.1 四条路对比

| 路线 | 做法 | 背景是否真在动 | 是否真实时 | 一张照片能否驱动 | 成本量级 |
|---|---|---|---|---|---|
| **a. 生成式流式渲染**（FlowAct-R1 / Vivix-A1） | Diffusion/自回归逐帧生成**整个人+背景**，模型自己决定人物走动、光影、环境 | ✅ 背景由模型生成，随剧情/动作变化 | ✅ 480P@25fps 流式；首帧 1.5s(论文)/2–3s(SDK文档)/约5s(API文档) | ✅ 单图即可，无需训练 | 3–4.2 万元/并发/月；Vivix 官方口径 <1 美元/小时但无公开单价 |
| **b. 预录实景视频底板 + 人像抠像合成** | 用可灵/即梦把老家的院子、厨房生成 10s 视频循环；数字人抠像贴上去 | ⚠️ 背景是**循环播放的固定素材**，会重复、不会回应 | ⚠️ 合成可实时，但背景永远在循环 | ⚠️ 需要数字人带**透明通道/绿幕**；现有 IVH 照片数字人输出是**带背景的成片**，抠不干净 | 视频素材 0.6–1 元/秒（一次性）；抠像服务 ~0.1–0.3 元/秒 |
| **c. 绿幕/透明通道数字人 + 背景图层** | 数字人层（alpha）+ 背景层（图片/视频/3D）合成 | ❌ 只有"背景动效"（平移/景深/光斑） | ✅ 实时 | ✅ 若供应商支持 alpha 通道（**IVH 照片数字人不支持**，需核实） | 低，但效果最假（人像贴纸感） |
| **d. 3D / NeRF / Gaussian Splatting 场景** | 重建真人 3D 头部 + 3D 场景，实时渲染 | ✅ 真正的 3D 背景，可运镜 | ✅ 实时（NeRF/3DGS 已可实时） | ❌ **一张照片建不出可靠 3D 头**（需多视角视频 + 训练，数十分钟~数小时 GPU） | 高，且需要家属提供大量素材 |

### 1.2 硬结论

> **用户想要的"人物动 + 背景也动 + 实时对话"，技术上一句话：只有路线 a（生成式流式模型）能做到，其余都是妥协。**
> 但路线 a 目前是**企业级定价**（3 万+/并发/月），个人开发者承受不起 →
> **可落地的最优解是"降级方案：点播式重逢"**（见第 3 节）：用可灵/即梦图生视频现场生成 5–10 秒"她在动、背景也在动"的视频，单条 2–6 元、单次通话 1–3 元，代价是每轮等待 20–60 秒（用"她正在想…"过渡动画 + 预热片段库掩盖）。

**关键补充（重要）**：如果家属能提供**逝者的老录像片段**，可改用**视频克隆形象**（火山边缘智能：建形象 2599 元/个，生成视频 **0.1 元/秒**；可灵数字人 0.4 元/秒）——比整段生成便宜 5–10 倍，且身份一致性远高于单图驱动。这条应作为点播方案的**首选素材策略**。

## 2. 两条路线的接入改造评估

### 2.1 公共改造：把数字人抽象成适配器（两条路线都必须先做）

现有 `js/ai-call.js` 把 IVH 逻辑硬编码在 `aiIvhCallFlow()` / `ivhSpeak()` / `aiIvhTrtc` 里，必须先解耦：

| 文件 | 动作 | 说明 |
|---|---|---|
| `js/avatar/avatar-adapter.js` | **新增** | 统一接口 `start(char)` / `speak(text, pcmStream)` / `interrupt()` / `stop()`，按 provider 分发 |
| `js/avatar/avatar-ivh.js` | **新增（迁出）** | 把 `aiIvhCallFlow`/`ivhSpeak` 原样搬出，保证不回退 |
| `js/avatar/audio-pipeline.js` | **新增（抽取）** | 把 `aiListenStart`/`aiUtterance`/`aiFloatToWav`/VAD 从 ai-call.js 抽出来，产出 **16kHz PCM 流**（火山/Vivix 都要这个） |
| `js/config.js` | 改 | 新增 `AVATAR_PROVIDER: 'ivh'\|'volc'\|'vivix'\|'ondemand'` + `realtimeServer` |
| `js/ai-call.js` | 改 | 只保留 UI/计时/记忆/字幕；`aiSpeak()` 改为调 `AvatarAdapter.speak()` |
| `index.html` | 改 | 增加 SDK script 位 + `#aicRemoteBox` 保持复用 |

### 2.2 路线 A：火山 FlowAct-R1（实时互动数字人 API）

**新增文件**
- `js/avatar/avatar-volc.js`：建连 → 传形象图 → 推 16kHz PCM → 收视频帧；心跳 + 会话时长上限（防崩坏）；动作 prompt 注入（"坐在老家院子里，看着镜头说话"）
- `server/realtime/index.js`：**常驻 Node WebSocket 服务**（`/ws/avatar`），浏览器 PCM ↔ 火山 API 双向桥接
- `server/realtime/volc-client.js`：火山鉴权签名、会话生命周期、断线重连

**现有 TRTC 代码能复用多少 → 约 30%**
- 火山出流是**火山 RTC / WebSocket**（非腾讯 TRTC），`TRTC.create/enterRoom/startRemoteVideo` 的"进房-订阅-渲染"三步**思想可复用、代码不可复用**；若火山支持 WHIP/FLV 出流，退化为直接喂 `<video>`，改造反而更小。
- ⚠️ 需核实：火山 API 版出流协议（WS 二进制帧 / RTC / WHIP），这决定前端改造量到底是 30% 还是 60%。

**云函数怎么办**
- **腾讯云 SCF 不能做 WebSocket 长连接**（HTTP 触发、短生命周期），必须新增常驻服务。
- 建议：SCF 保留做无状态 action（usersig / chat / asr / avatar-token 临时密钥签发）；长连接放 **腾讯云轻量应用服务器（2C4G，约百元/月）或函数计算 FC（支持 WS）**。
- ⚠️ 密钥绝不能下发给前端：SCF 签 **STS 临时令牌**，`avatar-volc.js` 只拿令牌。

**音频链路与瓶颈**
```
麦克风 → VAD断句(900ms静音) → WAV上传 → SCF asr(一句话识别) → LLM(glm-4-flash 非流式)
      → TTS → PCM → WS → 火山数字人 → 视频流 → 播放
```
| 段 | 现状耗时 | 是否瓶颈 | 优化 |
|---|---|---|---|
| VAD 断句 | 0.9–1.5s | ⚠️ 是 | 静音阈值 900ms → 400–500ms |
| ASR（含 WAV 上传 SCF） | 0.5–1.0s | 中 | 改**流式 ASR**，边说边识别；WAV 直传常驻服务省一跳 |
| LLM 非流式 | 0.5–1.5s | ⚠️ 是 | 改流式，按句切分，首句即送 TTS |
| TTS | 0.5–1.0s | 中 | 流式 TTS，边生成边推 PCM |
| **数字人首帧** | **1.5–5s** | **✅ 最大瓶颈** | 无法优化，只能靠"thinking 动画"掩盖 |
| **合计** | **3.9–9.5s** → 优化后 **2.5–4s** | | |

**工作量：约 11 人天**（常驻服务 3d + 前端适配器 3d + 音频流水线改造 3d + 联调降级 2d）

### 2.3 路线 B：Vivix-A1

**新增文件**
- `js/avatar/avatar-vivix.js`：WS 控制通道（创建会话 / 推音频 / `interrupt` 打断）+ **TRTC 拉流（直接复用 `aiIvhTrtc` 那套）**
- `server/realtime/vivix-client.js`：Vivix API 鉴权 + 会话代理（密钥隔离）

**现有 TRTC 代码能复用多少 → 约 90%**
- 官方口径：音视频经 **TRTC** 传输、控制走 WebSocket。→ `aiIvhTrtc = TRTC.create()` / `enterRoom` / `REMOTE_VIDEO_AVAILABLE` → `startRemoteVideo` **几乎原样复用**，只需把 `cfPost('create')` 的返回源换成 Vivix，并把 `drive(文本)` 换成 **WS 推 PCM 流**。
- `trtc-call.js` 无需改动。

**云函数怎么办**：同上，SCF 保留无状态；新增常驻 WS 服务（仅做控制面代理 + 密钥隔离，比路线 A 轻）。

**音频链路与瓶颈**：与 A 相同，但 **A1 是原生全双工**（语音语义直接在多模态空间建模，不走 ASR→LLM→TTS 级联），若使用其原生对话能力，可**砍掉 ASR+LLM+TTS 三段**，端到端 TTFR <1.7s；代价是**失去对"她说过的话"的文本控制 + 记忆库注入失效**（现有 `memAdd`/记忆召回依赖文本）。
→ 建议：**保留自己的 ASR+LLM+TTS**（保住记忆库 + 人设），只用 A1 做"形象+动作"渲染，牺牲约 0.5s 延迟换取可控性。

**工作量：约 8 人天**（WS 代理 2d + 前端 2d + 音频链路 2d + 联调 2d）

### 2.4 两路线对比

| 维度 | A 火山 FlowAct-R1 | B Vivix-A1 |
|---|---|---|
| 首帧 | 1.5–5s | <0.6s 可见反应，TTFR <1.7s |
| 背景动 | ✅（肢体+场景） | ✅✅（可走动、拿物品、开放世界） |

| 可拿性 | 官网可申请（需联系商务确认资源） | **内测排队（Join Waitlist）** |

## 3. 降级方案：点播式重逢（预算内可落地，推荐先做）

### 3.1 思路
**不追求实时，追求"每一句都像真的"**：每轮对话生成一段 5–10 秒的"她在动 + 背景在动"的视频，用等待动画 + 预热片段库把延迟藏起来。

### 3.2 三层架构（优先级从高到低，逐层能力递增）

| 层 | 触发 | 延迟 | 单价 | 说明 |
|---|---|---|---|---|
| **L1 预热片段库** | 命中高频意图（问候/想你/吃饭/身体/晚安/工作…） | 0s | 0（一次性） | 首次创建角色时**批量预生成 20–30 条**通用回复视频（可灵数字人 0.4 元/秒 × 5s ≈ 2 元/条 ≈ 60 元），存对象存储 CDN |
| **L2 现场生成**（点播） | 未命中 | 20–60s | 2–6 元/条 | ASR→LLM→TTS→提交视频生成任务→轮询→播放 mp4 |
| **L3 实时兜底** | 供应商额度到位后 | 2–4s | 高 | 切换 `AVATAR_PROVIDER='volc'/'vivix'`，前端无感 |

### 3.3 数据流（L2）
```
用户说话 → VAD → ASR(text) → 记忆召回 + LLM(text)
   → cloud-function action:'ondemand-submit' {charImageUrl, audioUrl|text, scenePrompt}
        ├ 素材策略①（有老录像）：视频克隆形象 + 音频驱动（火山边缘智能 0.1 元/秒）
        └ 素材策略②（只有照片）：可灵 3.0 图生视频/数字人（0.4–0.8 元/秒）
   → 返回 taskId → 前端显示"她正在想…"（复用 aicListen UI + 照片缓慢缩放/呼吸动效）
   → action:'ondemand-status' 轮询（3s 一次，60s 超时）
   → 拿到 mp4 URL → <video> 播放并写入本地片段缓存（同句二次命中直接走 L1）
```

### 3.4 文件设计

| 文件 | 动作 | 内容 |
|---|---|---|
| `js/avatar/avatar-ondemand.js` | 新增 | `speak(text)`：查本地缓存 → 查预热库 → 提交任务 → 轮询 → `playVideo(url)`；超时降级为照片+TTS |
| `js/avatar/clip-cache.js` | 新增 | IndexedDB/localStorage 片段索引（key = 角色ID + 意图标签 + 文本哈希），命中即播 |
| `js/avatar/intent-match.js` | 新增 | 复用 `ai-call.js` 里 `aiReply` 的正则规则表，把用户输入映射到预热意图（零额外模型成本） |
| `cloud-function/index.js` | 改 | 新增 `action: 'ondemand-submit'` / `'ondemand-status'` / `'warmup'`（首次建角色批量预生成）；保留 usersig/chat/asr/close |
| `js/config.js` | 改 | `AVATAR_PROVIDER: 'ondemand'` + `VIDEO_VENDOR: 'kling'\|'volc-edge'` |
| `js/ai-call.js` | 改 | `aiSpeak()` → `AvatarAdapter.speak()`；新增"她正在想…"状态 |

**成本测算**：新角色一次性预热 ~60 元；每次通话 8–12 轮，其中 5–7 轮命中 L1（0 元）、3–5 轮走 L2（2–6 元）→ **单次通话约 6–30 元**，个人开发者可承受（可做成"每次通话消耗 1 张重生卡"的商业模式）。

**工作量：约 5 人天**（云函数 2d + 前端播放/缓存 2d + 预热策略 1d）

## 4. 风险清单

| # | 风险 | 等级 | 触发条件 | 缓解措施 |
|---|---|---|---|---|
| R1 | **端到端延迟 4–10s，不像"视频通话"** | 高 | 全程 | ①VAD 降到 400ms ②LLM/TTS 全流式 ③"她正在想…"+点头/呼吸动效掩盖 ④首句用预热片段秒回 |

| R5 | **供应商内测拿不到额度**（Vivix 仅 Waitlist + Enterprise 定制，无公开单价；火山需联系商务确认资源） | 高 | 立项即触发 | ①**两条腿走路**：降级方案先上线，实时方案并行申请 ②准备 Demo（现有站点 + 用户故事）提申请，提高过审率 ③设 3 个月期限，拿不到就长期维持降级方案 |
| R6 | **成本失控**（单并发 3 万/月；点播被刷量） | 中 | 有真实用户后 | ①点播按次计费/购卡制 + 单用户日限额 ②实时方案只在付费时段启用，闲时切降级 ③账单告警 |
| R7 | **SCF 无法承载长连接** | 中 | 走实时路线 | 新增常驻服务；SCF 只做无状态 + 令牌签发（见 2.2） |
| R8 | **单图驱动效果不达预期**（动漫/侧脸/低清照片驱动差；火山明示"半身简单背景图最佳"） | 中 | 用户上传老照片 | ①上传端做照片体检（正脸检测/清晰度/尺寸），不合格引导重传 ②用图像修复/超分预处理老照片 |

## 5. 需联网核实 / 待确认项

1. 火山**实时互动数字人 API** 的出流协议（WS 二进制帧 / 火山 RTC / WHIP）与首帧实测（文档 2–5s 说法不一致）。
2. 火山是否有**按量/按时长**计费（目前查到的只有 1 并发包月 3 万 / 包年 30 万；SDK 版 4.2 万 / 42 万）。
3. Vivix-A1 **API 实际单价与是否对个人开发者开放**（目前仅 Enterprise 定制，无公开价格）。
4. 腾讯云 IVH 照片数字人是否支持 **alpha 透明通道**（决定路线 c 能否成立）。
5. 可灵「数字人」0.4 元/秒接口是否支持**图片 + 音频**输入（而非必须视频）。
6. 火山边缘智能 0.1 元/秒数字人视频的**形象创建素材要求**（是否接受家属提供的老录像片段）。
7. 上述**合规条款**需法务确认。
